## 1. 决定与前提

- 2026-11-21 起，本工程脱离上游 dolag233/Serpent 独立开发，不再合并上游。`upstream` 远端可以保留作参考，不作为合并来源。
- 后端保持 Electron + Node，不迁移 Rust。只有经测量确认的性能瓶颈才考虑 napi-rs 原生模块（第 5 节）。
- Ouro 是唯一的通用文件库（2026-11-21 用户决定）：管理各种类型的文件，按文件类型用插件提供元数据、缩略图、预览，按类型设置打开方式。专用软件（如 Panthesia，Rust + Tauri）作为外部程序从 Ouro 打开文件；数据跟着文件走（3.6）。
- Ouro 内部分为三个包，合称 **Keel**：`@ubik/protocol`（类型约定）、`@ubik/workbench`（界面层）、`@ubik/library`（资源库核心）。目前只有 Ouro 使用，放在本仓库 `packages/` 下；出现第二个需要嵌入这套界面或资源库的程序时，再拆为独立仓库 `D:\CS\_tools\keel`。
- 工程改名为 **Ouro**（2026-11-21 决定，取自 Ouroboros 衔尾蛇）。元数据目录 `.serpent` 同步改为 `.ouro`（第 6 节）。MIT 许可允许改名再发布，义务是保留原版权声明与许可全文。
- P0–P5 是重构，唯一新增的行为是左右栏开合状态的记忆。列表视图、方向键导航、键盘选择等新交互不做（2026-11-21 用户决定）。PF 增加文件类型、打开方式与伴生文件（3.6），PL 抽出资源库核心，PR 把自动任务改造为 AI 编写的规则系统（3.4、3.5）。
- 外壳只保留 Islands，删除 legacy 变体。

## 3. 目标结构

### 3.1 `@ubik/workbench`

**位置与许可。** 放在本仓库 `packages/workbench`（npm workspaces）。包内不引用 Ouro 业务代码，保持可以拆出的边界；拆为独立仓库 `D:\CS\_tools\keel` 的时机见第 1 节。

**为什么与 `@ubik/library` 分为不同的包。** 两者运行在不同进程：workbench 在渲染进程（浏览器环境，React），library 在后端进程（Node，带 SQLite 等原生依赖）。分成两个包，渲染层打包不会引入原生依赖，后端也不会引入 React；只用其中一个的应用也能单独依赖。两者共享的类型（项、字段、视图预设、传输接口、Result）放在第三个包 `@ubik/protocol`，不含运行时依赖。三个包同在本仓库，改动跨包时一次提交完成。许可 MIT，保留来源说明。

**依赖。** 只依赖 `react`、`react-dom`（peer）和 `zustand`（peer）。不依赖 Electron、Tauri、zod 以外的运行时库；不含 i18n 目录、图标集、业务类型。

**内容。**

| 模块 | 内容 |
| --- | --- |
| `tokens` | token 合同（名称、语义、明暗两套默认值）、`tokens.css`、TS 常量、层级 z-index |
| `shell` | 三栏外壳、`ResizeHandle`、栏宽拖拽 / 自动隐藏 / 双击复位 / 边缘拉回、宽度持久化、**开合状态持久化（新增）** |

| `collection` | 虚拟化数据源接口；现有的等高行与瀑布两种布局，行为不变；可见范围回调；命中测试索引 |

**宿主接口（与传输无关）。** 工作台不直接调用后端，只通过宿主注入的接口取数据：

```ts
interface WorkbenchHost {
  storage: KeyValueStorage;            // 偏好持久化；Ouro 用 localStorage 或 IPC
  platform: 'windows' | 'mac' | 'linux';
  labels: WorkbenchLabels;             // 工作台自身的文字，由宿主按语言提供
  icons: IconRenderer;                 // 图标由宿主提供
  clipboard?: ClipboardPort;
}

interface CollectionSource<TItem, TId> {
  total(): number;
  getEntry(index: number): { id: TId; item?: TItem; aspect?: number } | undefined;
  requestRange(start: number, end: number): void;   // 宿主自行决定 IPC 或 invoke
  subscribe(listener: () => void): () => void;
}
```

应用侧的传输模式统一为"一个出口 + 判别联合 + Result + 事件订阅"：

```ts
interface AppTransport<TRequest extends { type: string }, TResult, TEvent> {
  send(request: TRequest): Promise<Result<TResult>>;
  subscribe(listener: (event: TEvent) => void): () => void;
}
```

Ouro 用 `ipcRenderer.invoke` 与 preload 事件实现。宿主接口与传输无关，保留以后拆出独立仓库的可能。此接口放在工作台的 `host` 模块中作为类型约定，工作台组件不使用它。

验收约束：包内代码与类型不出现 `window.ouro`、`electron`、`@tauri-apps`、Ouro 业务类型（`AssetSummary` 等）、应用前缀的存储键。用 ESLint `no-restricted-imports` 与一个扫描测试强制执行。

规则：

- 组件用选择器直接订阅所需切片，不逐层传 props。一个组件的 props 只保留它自身的输入（id、变体），目标 ≤ 10 个。
- 跨领域动作写成具名的协调函数（如 `openLibrary`、`closeLibrary`、`resetLibraryScope`、`applyWorkspaceSnapshot`、`clearFilters`），集中在 `stores/actions/`，替代分散的 setter 序列与 effect 链。
- 后端事件在 `app/` 的单一订阅层处理，分发到 store，不在组件内订阅。
- 镜像 ref 全部改为 `store.getState()`。

### 3.3 样式

- **token 层**：`--ui-*` 为唯一 token 名称空间；旧别名删除。补齐阴影、混色（如 `--ui-wash-hover`）、圆角档位、毛玻璃、动效时长与曲线 token。明暗差异只在 token 中体现。
- **结构层**：每个组件同目录的 `*.css` 只写布局与几何（display、grid、flex、position、尺寸、间距、overflow、z-index 引用）。工作台组件的结构样式随包分发。
- **美术层**：颜色、背景、边框、阴影、圆角、透明度、滤镜、字体只引用 token，不出现字面值。可以与结构层同文件，但分为两个规则块；Stylelint 规则检查美术属性只允许 `var()`。
- **主题**：主题配置只改变 token 值（现状已满足）；删除组件级 `[data-theme]` 覆盖。
- **Islands 与 legacy**：二者是结构变体而非主题。保留 Islands（现为默认），删除 legacy 及其设置项；Islands 规则并入基础规则，去掉 `[data-shell-layout="islands"]` 前缀。
- `styles.css` 最终删除。

### 3.4 资源库核心 `@ubik/library`

用户 2026-11-21 决定：通用工具的范围扩大到数据层。资源库核心与 `@ubik/workbench` 并列，TypeScript（Node）实现。

**内容**：资源库与会话；实体文件夹与链接文件夹（含路径规则）；标签与标签层级；规则运行时（3.5）；扫描、监听与对账；查询与搜索表达式求值；操作历史与撤销；数据库迁移框架。

**不含**：具体格式。资源库中的一项就是一个文件。应用只通过一个扩展点注册**格式处理器**：给定文件，返回元数据字段与缩略图。图片、视频、3D 等由 Ouro 内置注册，MIDI、MusicXML 由 Panthesia 提供的 Ouro 插件注册。"同名文件归为一首歌"等组织需求由脚本规则完成（如打标签、写字段），核心不提供识别器或自定义视图机制。

**来源**：从 `src/worker/library-service.ts`（52,331 行）中按领域拆出。媒体处理（sharp、ffmpeg、OIIO、PDF、FBX）、AI、WebDAV 同步、Billfish / Eagle 接管留在 Ouro。

**Panthesia 不使用 `@ubik/library`**：Panthesia 是外部演奏程序，保留 Rust + Tauri，通过文件与 Ouro 配合（3.6）。

### 3.5 规则系统

用户 2026-11-21 决定："自动任务"改名为"规则"。**规则只有一种：脚本**。不做结构规则、识别器或文件夹视图规则；不提供可视化参数配置。规则由 AI 编写和修改。

**模型**

- 一条规则 = 一个 TypeScript 脚本 + 一份清单（名称、用途、触发、目录范围、权限）。
- 触发：导入后、文件变化、定时、手动；或持续运行。
- 执行：在现有 QuickJS 沙箱中运行，通过领域 API 调用 Automation Gateway，与人类操作走同一条路径（同一套校验、撤销、提示）。
- **优先级 = 列表顺序**：规则在列表中分组排列，可拖动排序；分组顺序与组内顺序共同决定优先级。同一时机触发多条规则时，按此顺序依次执行，后执行的规则看到前一条的结果。现有迁移 64 的 `automatic_task_layout`（任务与分组顺序）直接沿用。
- 开关、顺序、分组、运行记录保存在数据库；脚本与清单保存为文件。

**界面**

- 侧栏规则列表：分组、可拖动排序、每条显示名称、用途、开关、最近一次结果。
- 点开一条规则：显示它的**触发历史记录**：每次触发的时间、触发原因、处理的文件数、产生的改动（可定位到资源、可撤销）、日志输出、错误（文件、行号）。
- 另有"复制给 AI"：把规则文件路径、当前内容和说明书位置整理成一段提示。

**AI 友好的编写环境**

1. **规则即文件**：资源库 `.ouro/rules/<规则 id>/` 下的 `rule.json` 与 `*.ts`，可以 diff、可以放进 Git。
2. **自带说明书**：`.ouro/rules/` 下生成 `AGENTS.md`（写法、约束、示例）、领域 API 的 `.d.ts`、`rule.json` 的 JSON Schema、典型示例。AI 打开这个目录就能写规则，不需要读 Ouro 源码。
3. **可验证**：MCP 工具与命令行提供 `rule.validate`（语法、类型、Schema、权限）、`rule.dry-run`（对指定范围试运行，返回将要发生的改动，不写入）、`rule.run`、`rule.history`、`rule.enable` / `disable`。
4. **可解释、可撤销**：每个改动记录来源规则与版本，撤销沿用操作历史。
5. **幂等与权限**：重复运行结果不变；脚本只能使用清单中声明的权限。

现有可以复用的基础：Automation Command Registry、Gateway、QuickJS 脚本沙箱与领域 API、自动生成的 `.d.ts`、内嵌 MCP 服务、`ScriptSandboxPreviewDialog`（试运行预览）、迁移 63 / 64 的自动任务与排序表。现有自动任务（add-tags）转换为等价的脚本规则。

### 3.6 文件类型、打开方式与伴生文件

用户 2026-11-21 决定：Ouro 是唯一的通用文件库，管理各种类型的文件；专用软件（如 Panthesia）作为外部程序，按文件类型从 Ouro 打开。数据尽量跟着文件走：专用软件把数据写在文件旁边，Ouro 负责让它们一起移动。

**文件类型插件接口**（在现有插件系统上扩展）：

| 接口 | 作用 | 例 |
| --- | --- | --- |
| 格式处理器 | 给定文件，返回元数据字段与缩略图 | MIDI：时长、BPM、调、轨道数、钢琴卷帘缩略图 |
| 预览器 | 在 Ouro 内查看该类型 | 图片、视频、PDF、3D（现有） |
| Inspector 分区 | 选中该类型时显示的分区 | MIDI 的轨道与手别摘要 |
| 打开方式 | 注册"用某程序打开"的条目 | "用 Panthesia 练习" |
| 伴生扩展名 | 声明某扩展名是主文件的伴生文件 | `.panthesia`、`.xmp` |

**打开方式**：设置页按扩展名指定默认打开方式（系统默认程序 / 指定外部程序 / Ouro 预览器 / 插件条目）；双击按默认方式打开；右键菜单"打开方式"列出全部可选项。外部程序以命令行参数接收文件的绝对路径。

**伴生文件**：

- 规则：同一目录下，与主文件同名（去掉扩展名后相同，或主文件全名加伴生扩展名，如 `photo.CR3.xmp`）且扩展名已登记为伴生的文件。
- 移动、改名、删除、回收站恢复、文件夹 / ZIP 导出、同步时，伴生文件与主文件一起处理；改名时伴生文件同步改名。
- 浏览时默认不作为独立资源显示，在主文件的 Inspector 中作为附件列出；设置中可以改为显示。
- 跨目录的引用（如清单引用另一个文件夹中的音频）由专用软件自己按内容哈希修复，Ouro 不改写伴生文件的内容。
- 文件夹级清单（如歌曲文件夹根目录的 `song.panthesia`）随文件夹整体移动，不需要额外处理。

**与 Panthesia 的配合**：Panthesia 提供一个 Ouro 插件：MIDI / MusicXML 格式处理器、钢琴卷帘缩略图、`.panthesia` 伴生扩展名与文档类型、"用 Panthesia 练习"打开方式。`.panthesia` 清单格式由 Panthesia 定义（见 Panthesia 的 `docs/development/current-plan.md`）。

## 5. 后端与 napi-rs

后端保持 Node。SQLite（better-sqlite3）、全文检索（FTS5 trigram）、向量检索（sqlite-vec）、图像处理（sharp）、PDF 栅格化（@napi-rs/canvas）已经是原生实现；视频与 EXR 走外部 ffmpeg / oiiotool。koffi 只用于系统接口（Job Object、剪贴板、IME、驱动器类型），不在热路径上。

**判断依据（全部满足才引入原生模块）**

1. 现有基准或新增基准显示该环节超出目标（如导入吞吐、首屏时间、交互请求 p95），且 profile 证明耗时在 JS 计算，不在磁盘或网络 I/O。
2. 该环节阻塞 Worker 事件循环，导致交互请求排队（`performance-contract` 的交互通道延迟上升）。
3. 先尝试纯 JS 修复（异步化、流式、分批让出、换用 Node 内建原生能力），仍不达标。
4. 没有成熟的现成原生 npm 包可用。
5. 收益足以抵消成本：三平台预编译、Electron ABI、打包与 `ensure-native` 维护。

**候选环节**

| 环节 | 现状 | 先做的纯 JS 修复 | napi-rs 价值 |
| --- | --- | --- | --- |
| 内容哈希（SHA-256） | `library-service.ts:5800-5830` 用同步 `readSync` + `crypto`，阻塞 Worker | 改为流式异步读取 + `crypto` 增量哈希（`crypto` 本身已是原生） | 低；只有在需要多线程并行哈希大批文件时才考虑 |
| 目录扫描与对账 | JS `readdir` 递归 + `fs.watch`（SMB/NFS 不可靠） | 分批让出、并发限制 | 中；大目录（数十万文件）首次扫描可用 Rust `jwalk` 并行遍历 |
| 调色板提取 | `palette-extractor.ts` 纯 JS 4096 桶直方图 + 聚类，像素由 sharp 解码 | 缩小采样尺寸 | 中低；先用 `test:perf:palette` 测量 |
| 文件头解析 | `image-dimensions`、`raw-image-metadata`、`raw-embedded-thumbnail`、`gif-metadata`、`font-file-metadata` 纯 JS | 只读必要字节 | 低；通常受 I/O 限制 |
| FBX 转换 | ufbx WASM + JS GLB 构建 | — | 低中；WASM 已接近原生，只有大模型批量时考虑 |
| 非 ZIP 压缩包 | `libarchive-wasm`，整包载入内存（有上限） | 流式读取或改由 Worker 处理 | 中；大压缩包内存占用是实际问题时可改原生 libarchive 绑定 |

结论：目前没有候选同时满足 1–5。P7 先用现有基准测量导入、扫描、调色板三项，再按依据逐项决定。
